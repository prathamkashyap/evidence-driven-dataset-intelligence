# Independent relevance benchmark protocol

**Status: proposed design; collection and annotation have not started.** Counts, time estimates, thresholds, and allocation rules below are proposals requiring author/supervisor approval. They are not completed sample sizes, labels, or results.

## Benchmark unit and alternative sizes

The descriptive unit is a task query with a frozen candidate-dataset-snapshot pool. The independent resampling unit is a predeclared task-family/dependency cluster. Exact or near-duplicate tasks and task briefs with a documented material dependency are connected into one cluster; all connected tasks remain in one split and one bootstrap cluster. Candidate pairs and pairwise training examples are not independent observations.

Two alternatives retain the same proposed task frame and 12/6/18 task split; only candidates per task differ:

| Item | Option A: broader pool | Option B: reduced pool |
|---|---:|---:|
| Task briefs | 36 | 36 |
| Modality allocation | 12 each: text, tabular, image | Same |
| Candidates per task | 36 | 24 |
| Task–candidate pairs | 1,296 | 864 |
| Independent first-pass ratings | 2,592 | 1,728 |
| Train / development / held-out tasks | 12 / 6 / 18 | Same |
| Ranking-blind base candidates per task | 18 (6 per source stratum) | 12 (4 per source stratum) |
| Retrieval contribution before overlap/fill | Up to 6 each from BM25, dense, RRF | Up to 4 each from BM25, dense, RRF |

Both options are proposed. Reducing candidates by one third reduces within-task breadth and, at most, pairwise training examples per task from 630 to 276; it does not increase the number of independent held-out task-family clusters. Option B may reduce judged-pool coverage opportunities and the chance of observing relevant candidates from the retrieval pool. It leaves the nominal query-level test size unchanged but can increase N/A outcomes if a task's smaller pool contains no assessable relevant candidate. Neither design supports catalogue-wide recall.

## Task source frame and eligibility

Build a dated frame from these source categories: public ML task/benchmark specifications; public scientific or technical papers that define a dataset-linked prediction or analysis task; and public institutional or domain challenge/task descriptions. No external task source is approved by this document alone. Before use, curators must register each actual source, version or date, retrieval route, terms/access status, and reproducible snapshot evidence. Do not name or rely on an unverified task catalogue.

An eligible task brief must have: a public, citable source; a clear objective and expected output; one supported primary modality (`text`, `tabular`, or `image`); a task type supported by `TaskSpecification`; enough information to create a structured task specification without inventing requirements; and a documented distinction from M8 tasks and any other sampled task family. Exclude briefs that require unsupported modalities or system behavior, rely on private or inaccessible labels, lack an identifiable target/output, duplicate an M8 task, or cannot be separated from a duplicate task family. Record every screened task and an exclusion code before sampling.

Register each mandatory constraint's applicability before candidate review. Constraints are `always` applicable unless a conditional rule is explicitly specified in advance. An assessor may mark a conditional constraint `not_applicable` only with evidence supporting that registered condition; this state cannot bypass an always-applicable requirement. `unknown` means an applicable constraint is unresolved by evidence, while `unassessable` means permitted evidence is insufficient to make a state judgment. Preserve both states separately and apply the predeclared unknown policy to either.

Use the current proposed modality-by-task-type allocation only if the screened frame can support it:

| Modality | Classification | Regression | Clustering | Detection | Total |
|---|---:|---:|---:|---:|---:|
| Text | 4 | 3 | 3 | 2 | 12 |
| Tabular | 5 | 3 | 2 | 2 | 12 |
| Image | 5 | 2 | 2 | 3 | 12 |
| **Total** | **14** | **8** | **7** | **7** | **36** |

Operational task-type meanings must be recorded in each task row: classification predicts a documented categorical label; regression predicts a documented continuous outcome; clustering groups records without using a supplied class target; detection identifies a specified event or localized finding. In text, detection means span/entity tagging; in tabular data, anomaly/event detection with its output defined; in images, object/region detection with the required localization annotation identified. A task is not classified as detection merely because its class is rare. The modality is the primary input consumed by the task; text attached to an image does not change an image task to text. Each brief must state the expected target/annotation structure and whether those labels are present, derived by a documented mapping, or absent.

If the proposed modality/type cells cannot be filled with eligible task-family groups, do not duplicate or split a family to hit quotas. Document the deficient cells and obtain approval for a revised allocation before retrieval or annotation.

## Task-family grouping and split allocation

Two curators independently screen and group task briefs before candidate retrieval or labels. A shared task-family group is required for exact/near-duplicate briefs, paraphrases of the same task, variants using the same benchmark/corpus and target definition, or tasks whose distinctions depend only on a benchmark split or superficial wording. Record evidence and rationale for each grouping and non-grouping. Resolve curator disagreement before sampling; preserve both initial decisions and the resolution. Also record `related_task_group` links for materially related but nonduplicate briefs where a shared data source, target construct, or closely related task formulation could cause information leakage. Assign each frozen brief a unique `task_id` derived as lowercase hexadecimal `SHA-256(UTF-8(canonical_source_uri + NUL + source_task_id_or_frozen_section_locator))`; the locator must identify the specific task definition in the frozen source snapshot and may not be an unversioned title alone. The **split/bootstrap cluster** is the connected component of task-family and registered material-dependency links. Define its `stable_cluster_id` as lowercase hexadecimal `SHA-256(UTF-8("phase2-task-cluster-v1\n" + newline-joined lexicographically sorted task_id values))`; task IDs cannot contain newlines. No component may cross a split, and a component moves as one resampling unit. Record component membership, linkage evidence, and the exact ID inputs.

Assign complete split/bootstrap clusters—not individual briefs—to train, development, or test. The proposed task targets remain 12/6/18, with 4/2/6 tasks per modality and the stated overall modality/type totals. Before benchmark construction, authors/supervisor must propose, approve, and freeze the split seed and deterministic assignment procedure along with the ordered eligible task frame, split/bootstrap clusters, and source snapshot. This proposal selects no numeric split seed. A versioned deterministic constrained allocator must (a) treat each cluster as indivisible, (b) meet exact split and modality counts and exact overall modality/type totals, and (c) minimize `Σ(m,t,s) (x[m,t,s] − N[m,t] × p[s])²`, where `x[m,t,s]` is the assigned task count, `N[m,t]` is the proposed modality/type total, and `p[s]` is 12/36, 6/36, and 18/36 for train, development, and test. Encode the seed as its decimal UTF-8 string. Among equal objective values, choose the lexicographically smallest ascending sequence of selected-cluster `SHA-256(UTF-8(seed + NUL + stable_cluster_id))` digests; among those memberships, sort clusters by digest and choose the lexicographically smallest assignment vector under split order train, development, test. Record allocator and solver versions, objective value, tie order, and group-to-split map. If no assignment meets the hard constraints, stop and revise the frame or counts before retrieval, candidate ranking, or annotation. Do not split a cluster, silently relax a stratum, or use test labels to adjust the split. The chosen integer-allocation implementation and objective must be frozen before task curation is finalized.

Candidate pools may still share dataset families across task splits in the primary analysis. Report documented cross-split family overlap before fitting. A separate family-disjoint sensitivity analysis is defined below; do not describe the primary task split as dataset-family-disjoint.

## Candidate catalogue frames and source strata

The candidate source strata are: (1) general dataset repositories; (2) institutional or domain repositories; and (3) curated benchmark/challenge catalogues. The repository's implemented adapters identify Hugging Face, OpenML, UCI, and Kaggle as candidate catalogue sources; each source is eligible only after its current access method, reuse terms, metadata availability, and snapshot procedure have been checked and recorded. These names do not imply that any source or particular record has been approved for collection. Do not bypass login, rate limits, terms, or access restrictions.

Maintain a source registry that assigns each catalogue a single primary stratum before screening. Use this precedence when a source could fit several strata: an institutional repository operated by the data owner is institutional/domain; a catalogue whose primary role is an explicitly curated benchmark/challenge collection is curated; otherwise use general repository. Candidate stratum follows the canonical record's authoritative host, not the dataset's topic. If a record has multiple authoritative hosts, use its predeclared canonical record; retain alternate provenance. If no primary stratum can be assigned, record `unresolved_stratum` and do not use it to satisfy quotas until curators resolve it without viewing ranking or judgment outcomes.

For each source and catalogue snapshot, preserve the source registry version, API/catalogue revision or capture date, query/configuration, retrieval timestamp, response/document hashes, software version, canonical candidate IDs, dataset version/revision, and access failure records. A seed does not reconstruct a changing catalogue; the frozen source response/snapshot and ordered eligible frame are required. Do not fetch full dataset payloads unless separately authorized and justified. A metadata-only failure or inaccessible documentation is not evidence of irrelevance.

## Candidate screening and deterministic pool construction

Apply objective screening before any ranking outputs are inspected: a candidate must have a stable source ID and version/snapshot identity, an accessible public record under approved terms, sufficient public documentation to create an evidence packet, and a record with stable identity and enough source information to support the proposed evidence packet. Exclude exact duplicates within a task pool using canonical source ID plus version/snapshot hash. Retain distinct mirrors or derivatives as separate candidates when the source records differ; attach documented family provenance. Record suspected mirrors separately. Do not remove candidates because an early relevance judgment or system score is unfavorable.

For each task:

1. Build a ranking-blind, source-stratified base: Option A selects 18 candidates, six per stratum; Option B selects 12, four per stratum. Screen candidates under the frozen query-relevance criteria using a recorded deterministic order/seed. Preserve screened and selected IDs, stratum, inclusion rationale, and exclusions.
2. Freeze a task-specific ordered screened frame artifact, source-stratum order, screening rule/review, and seed before inspecting retrieval outputs. The proposed tie order is general repository, institutional/domain, then curated benchmark/challenge, following the numbered source-stratum definition above; this is a proposed deterministic convention that authors/supervisor must approve before protocol freeze. Select the first six (Option A) or four (Option B) frame candidates from each stratum. Record each stratum's required and available counts; any quota shortfall needs an approved, reasoned review before annotation.
3. Run exactly one BM25, one dense MiniLM, and one RRF retrieval configuration per task against the same frozen catalogue snapshot and frozen task query artifact. Preserve raw top-six outputs, score, rank, run configuration/version, and the tie rule: score descending, then candidate ID ascending. The unique-candidate union is traversed rank-wise in fixed method order BM25, dense MiniLM, RRF. Only the first six newly contributing candidates per method in Option A or four in Option B may enter through retrieval; later overlaps remain provenance but do not change a candidate's first selection route. No retrieval fallback is registered in this proposal: a failed required run is recorded and pool freeze stops pending an approved protocol/configuration resolution.
4. If overlap leaves the pool short, fill from the frozen screened frame using the registered stratum order, preferring the stratum with the lowest current pool count; ties use the registered stratum order, then frozen within-stratum frame order. Preserve every retrieval overlap as a separate inclusion reason. The ordered final candidate IDs must be exactly replayable from the frozen frame, raw runs, caps, and fill rule. A final pool shortfall requires a separate approved review and flow record before annotation; ranking-blind selections must still comprise at least half of the actual pool. If the independent base cannot meet that minimum, stop and obtain approval for a revised target.

Candidate identity includes stable source name, native source ID, version/revision, canonical URL, snapshot hash, and a distinct family-link record. Freeze task/pool membership, source packets, query strings, retrieval outputs, family-link evidence, configurations, seeds, software/model revisions, and hashes before annotation. A candidate access failure before pool freeze may be replaced only using the rule above and must remain in the flow log. After freeze, do not replace it; if its evidence cannot support judgment, record unassessable and the access reason.

A future data-validation implementation should treat exact source/native-ID/revision/snapshot identity as the duplicate key. Possible cross-source aliases or mirrors remain separate records unless a curator records a canonical relation and review; this rule does not infer that related records are duplicates.

The mixed pool intentionally includes candidates retrieved by the methods evaluated. Report **judged-pool Recall@6** only. State independent/retrieval inclusion counts and overlaps. This measure does not estimate relevance outside the judged pool and is not unbiased catalogue-wide or live-discovery recall.

## Dataset-family identity and family-disjoint sensitivity

Distinguish three relations: (a) documented same-family/lineage supported by source provenance or authoritative record links; (b) a Phase I detector-inferred relation; and (c) unknown/no documented relation. Record the relation source and evidence. Do not promote detector-inferred links to documented facts or use them to silently merge candidate IDs. Primary family and redundancy summaries use documented links; report inferred links separately.

The primary train/development/test split is task-family-disjoint, not candidate-family-disjoint. As a prespecified secondary sensitivity, create a family-disjoint Track B test view by removing from each test task candidates whose documented family appears in any train or development pool. Also remove candidates whose family status is unknown from this sensitivity view, because absence of a recorded link does not prove family independence. Retain test task assignments and original pool in the primary analysis; do not move a task or candidate across splits. Recompute the conditional ranking metric and its eligible/positive denominators on the remaining candidates without looking at the resulting system contrast while defining the view. Report the number of removed candidates by reason, per-task remaining pool, and N/A outcomes.

Treat the family-disjoint sensitivity as usable for an aggregate contrast only if at least 12 independent test task-family clusters remain evaluable, with at least four such clusters in each modality. This is a reporting-completeness threshold, not a power guarantee. Otherwise report its per-task values and counts but mark the pooled contrast and interval N/A. If detector-inferred families are used for an additional sensitivity, label it separately and never substitute it for the documented-family analysis.

## Annotation independence, packet changes, and custody

Recruit two independent assessors who did not implement Phase I ranking, author sampled task briefs, select candidates using ranking outputs, or train the proposed model. Use a third independent adjudicator who had none of those roles and did not curate the task/candidate frame. The adjudicator must remain blind to method, score, rank, native gate decision, and study hypothesis direction. If those independence conditions cannot be met, pause and seek a revised design; do not call project-author judgments independent.

Each assessor receives the same versioned task brief and candidate evidence packet, with candidate order randomized independently. Hide system rankings, scores, roles, method names, candidate inclusion reason, split membership, native gate decisions, and other assessor responses. Assessors may inspect only registered public sources under the rubric. Log every supplementary check (source URI/type, access time, retrieved version/hash, exact claim/observation, and reason) with a pseudonymous assessor ID and pair ID.

If a source check reveals materially missing or incorrect packet evidence, the assessor records a packet-correction request without changing or erasing the first-pass judgment. A separate packet custodian verifies and versions the corrected packet, then distributes the same correction to both assessors without revealing who requested it or either first-pass response. Represent each packet/rubric version as a separate annotation round; both assessors independently re-rate every affected pair in the new round, preserving old records and linking the superseded round. A correction requires a recorded reason and approved packet-correction review. Only an unfinished round may be superseded. A finalized pair cannot be reopened without a separately approved protocol amendment. Adjudication is linked to the current round and can occur for one pair while annotation continues on others. Do not share a test-packet correction or any test label with model developers before the authorized one-shot evaluation.

## Calibration, workload check, and adjudication

Before any calibration, authors/supervisor must provisionally approve a limited calibration plan, personnel, and preliminary resource envelope. Obtain all required ethics, consent, source-access, privacy, and retention approvals before conducting calibration with people or research materials. Only then may assessors be trained on a separate calibration set of 24 source-supported or hypothetical cases that are not M8 records and are not candidates, tasks, or snapshots in any final benchmark split. Calibration cases are not benchmark records, are not used for model fitting, and cannot be added to the benchmark. No calibration judgments have been created or authorized by this protocol revision.

Proposed calibration gate (requires approval): before ratings, freeze a case-to-category coverage matrix for these seven boundary categories: grade 0 versus 1; grade 1 versus 2; grade 2 versus 3; unassessable evidence versus affirmative evidence of non-relevance; ordinary preprocessing versus creation of labels or task redefinition; partial population coverage versus genuine incompatibility; and unknown mandatory constraint versus confirmed violation. The 24-case calibration frame must contain at least four cases assigned to each category; one case may cover multiple categories. At least 20 cases must be jointly assessable and at least 12 applicable constraint assessments must be available, or calibration is inconclusive and a replacement disjoint set is required. After orientation and discussion of rubric application, each assessor independently rates the same set. Require (i) at least 80% exact relevance-grade agreement on mutually assessable cases; (ii) at least 95% agreement within one grade; (iii) at least 90% exact assessability agreement; (iv) at least 90% exact applicable-constraint-state agreement; and (v) no unresolved systematic confusion in a grade-boundary category. Also report the category-specific confusion table and weighted kappa descriptively; do not treat a small calibration kappa as proof of reliability. If a threshold is missed or a systematic boundary issue remains, pause, revise/version the rubric, retrain, and repeat once on a new disjoint calibration set. A second failure stops annotation pending supervisor review; do not lower criteria after seeing results.

Measure actual active judgment time per item, excluding breaks, and calibration/adjudication time per case. Record elapsed durations under pseudonymous IDs without collecting unnecessary wall-clock patterns. Use the observed calibration distribution to update the workload forecast; after reviewing calibration evidence and workload implications, authors/supervisor must explicitly select Option A or B. This calibration is feasibility work, not a benchmark pilot and cannot estimate benchmark label quality.

For benchmark annotation, preserve both independent first-pass records. Send one pair to the adjudicator if any relevance grade differs, assessability differs, or any applicable constraint state differs. Count a pair once in the disagreement/adjudication numerator even if several fields differ. The adjudicator sees both rationales, records a separate final label/state/reason, and cannot overwrite either first-pass record. The predeclared pause threshold is **more than 25% of unique pairs requiring adjudication**. Apply it at two levels: after each whole-task batch, pause all further work if that batch exceeds 25%; also compute the cumulative rate within each split after each batch and pause that split if it exceeds 25%. The task batch is all pairs for one task; if task-family groups share a split, preserve group assignment. A pause triggers rubric review without system scores, protocol versioning, and a decision to re-annotate affected material or stop. Do not discard disagreements or difficult pairs to get below the threshold.

The independent test-label custodian controls secure storage, developer access authorization, sealed-test release, and access audit records. Authorized assessors may access the held-out evidence needed for independent judgments, and the authorized adjudicator may inspect the relevant first-pass judgments and evidence to resolve a disagreement. Assessors must not see one another's first-pass judgments before submitting their own. System developers and ranker operators must not receive sealed judgments before authorized evaluation. All access must be role-scoped, recorded, and governed by the approved privacy and retention plan. The custodian may release only protocol-approved aggregate integrity counts that cannot identify a candidate or expose labels; do not release per-task scores, label examples, or outcome-dependent feedback to developers. Train/development labels may be opened only after their split and access permissions are recorded. Test relevance and eligibility remain sealed together from developers until code, features, baselines, exclusions, and analysis are frozen and the one-shot access is approved.

## Workload scenarios (planning assumptions, not observed times)

The following estimates are person-hours and deliberately separate task/candidate work from assessor time. Assumptions: 1–2 total curator-hours per selected task (two curators each spend 0.5–1 hour); 3–6 minutes per task-candidate slot for source/identity/family screening; 4–8 minutes per slot for packet assembly and provenance; first-pass rating central assumption 2.5 minutes with 2–4 minute sensitivity; calibration/training 8–12 hours total; each adjudicated pair takes 2.5–5 minutes for the adjudicator; provenance QA samples 20% of task-candidate packets at 3–5 minutes each as a minimum proxy; custody/final audit takes 12–20 hours. Source-frame discovery, legal/ethics review, platform outages, substantial packet correction, and re-annotation are not included, so totals may be higher.

| Work component | Option A (36 candidates/task) | Option B (24 candidates/task) |
|---|---:|---:|
| Task-frame curation (36 × 1–2 h) | 36–72 h | 36–72 h |
| Candidate screening/provenance (3–6 min per pair) | 65–130 h | 43–86 h |
| Evidence packet preparation (4–8 min per pair) | 86–173 h | 58–115 h |
| First-pass judgments at 2–4 min each, both assessors total | 86–173 h (base 108 h; 43–86 h each assessor) | 58–115 h (base 72 h; 29–58 h each assessor) |
| Calibration and training | 8–12 h | 8–12 h |
| Provenance audit proxy (20% packets × 3–5 min) | 13–22 h | 9–14 h |
| Custody and final review | 12–20 h | 12–20 h |

Adjudication sensitivity, shown separately because it depends on disagreements across grade, assessability, and constraints:

| Unique-pair disagreement rate | Option A cases; adjudicator hours at 2.5–5 min/case | Option B cases; adjudicator hours at 2.5–5 min/case |
|---:|---:|---:|
| 10% | ≈130; 5.4–10.8 h | ≈86; 3.6–7.2 h |
| 25% | 324; 13.5–27 h | 216; 9–18 h |
| 40% | ≈518; 21.6–43.2 h | ≈346; 14.4–28.8 h |
| 60% | ≈778; 32.4–64.8 h | ≈518; 21.6–43.2 h |

At the 25% disagreement scenario, component-wise planning envelopes are approximately **320–628 person-hours for A** and **232–453 for B**. At 60% disagreement and five minutes per adjudicated case, the upper envelopes rise to approximately **666 h for A** and **478 h for B**. These are arithmetic planning scenarios, not predictions or observed workload. Option B saves roughly one third of pair-level screening, packet, annotation, and adjudication work, but not task curation or the independent-task-unit count. The 20% audit estimate is a lower proxy if a candidate packet contains multiple source claims; budget from the actual registered claim-reference count before approval.

**Conditional feasibility recommendation:** choose A only if the team can resource its broader judged pools and approximately 320–630+ person-hour planning envelope, including a funded adjudication reserve. Prefer B for a bounded conditional-ranker comparison only if the supervisor accepts narrower pools and the team can resource approximately 230–455+ hours plus source-frame discovery and correction contingencies. If neither fits, pause and redesign the estimand and task count before sampling; do not quietly shrink a frozen pool. The sequence is: provisionally approve the alternatives, limited calibration plan, personnel, and preliminary resources; obtain required governance approvals; conduct only the authorized calibration; review its evidence and workload implications; explicitly select A or B with an approved budget; then freeze the selected benchmark construction plan before full-scale annotation. The final size choice remains pending author/supervisor approval, and calibration is not currently authorized.

## Human governance, retention, and release

Before recruiting anyone or collecting annotations, authors and supervisor must approve the final protocol, study purpose, size, rubric, assessor compensation/time commitment, and publication claims. The supervisor/institution must determine whether ethics/consent review is required and approve the consent, source-display, and retention rules; no such approval is claimed here. Source terms and any display/copying restrictions must be checked before packet preparation.

Roles are distinct: two task/candidate curators create and freeze frames; two independent assessors annotate; a third independent person adjudicates; and a test custodian outside model development stores test judgments and controls one-shot access. Record conflicts of interest and signed role/independence declarations. Supervisor/author approval is required before protocol freeze, before benchmark acquisition, before annotation launch, and before test-label opening/public release.

Use pseudonymous assessor IDs. Keep any contact/consent key separate from annotation data in access-controlled encrypted storage; do not collect names in annotation records. Preserve first-pass labels, adjudications, source provenance, packet versions, and access audit events. A proposed retention rule is to delete the re-identification key and direct contact details 90 days after collection closes unless an institutionally approved longer period is required; retain only deidentified ratings/provenance for the period explicitly approved in the consent and research record. If the institution's requirement differs, record the exact governing rule before recruitment. Public exports require a custodian privacy review, removal of identifying notes/timestamps/source details where needed, and confirmation of consent and source permissions. Keep restricted records private; release only approved pseudonymized aggregates or records.

## Exclusions and current state

Exclude only by predeclared objective reasons: duplicate frozen snapshots, corrupted/empty packets, inaccessible source material that prevents judgment, unsupported task representation, or unresolved assessor conflict under the adjudication guide. Record exclusions by split, modality, task type, source, and reason. Relevance-unassessable pairs remain in the assessability accounting and are not relabeled grade zero. Do not exclude a pair because it lowers a score or is difficult.

No task frame, catalogue snapshot, candidate pool, calibration set, judgment, model, or Phase II result is created by this proposal. Candidate-source acquisition, calibration, annotation, and training remain unauthorized until separate human approval.
