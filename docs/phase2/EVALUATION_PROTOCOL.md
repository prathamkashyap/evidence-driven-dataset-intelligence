# Phase II evaluation protocol

**Status: proposed; no metrics, model fits, or experiments have been run.** This revision clarifies comparison tracks and metric semantics. It is not a preregistration approval. The authors and supervisor must approve the changed primary comparison and remaining decisions before freezing the protocol, labels, model, or analysis.

## Evaluation tracks and eligibility

Keep one frozen, unfiltered candidate input pool for each task and preserve each method's native eligibility/gate decision and emitted list. Independent adjudicated eligibility is ground truth for evaluation; it is not input to the Phase I gate and must never be used to prefilter candidates in the native system track.

### Track A — Native system and gate behavior

Run the unmodified Phase I recommendation path with only its original recommendation-time evidence inputs, hard gates, scoring, selector, and target size `k=3`. Do not supply adjudicated eligibility to the system or remove candidates from its input pool using annotation outcomes. Persist the entire input pool, native gate decisions and reasons, and emitted R3 list. After execution, compare those decisions and outputs with the independent task–candidate judgments.

Phase I gates are limited to the implemented checks in `src/dataset_intelligence/utility/estimator.py`: confirmed modality mismatch, a recorded licence string matching a task's prohibited-licence substring, and a Kaggle record when public anonymous access is required and gated access is not allowed. They do not implement the full Phase II eligibility policy. Report gate decisions against each applicable adjudicated constraint separately; do not describe the result as general eligibility classification. For emitted R3 candidates, report confirmed mandatory-constraint violations, policy-ineligible/unresolved outcomes, unknown-constraint exposure, and unassessable constraint judgments separately. A zero observed violation count is a result on this evaluated pool, not proof of universal safety.

Track A supports the native operational output and observed gate-behavior question (RQ3b/H3). It does not estimate ranking quality after oracle filtering.

### Track B — Oracle-filtered conditional ranking

For each task, construct one common conditional pool from the independently adjudicated labels, using the task's frozen constraint policy. Include candidates classified eligible; include `eligible_with_unknown` only when that task permits the property to remain unknown. Exclude `ineligible_confirmed_violation`, `ineligible_unverified_required`, and `unresolved` candidates from the Track B pool. Apply exactly this same pool to every compared ranking method, regardless of that method's native gate decision; do not apply a second method-specific eligibility filter. The pool is an oracle-filtered evaluation condition: it measures relevance ranking conditional on adjudicated eligibility, not the system's ability to find eligible candidates or its gate accuracy. Do not call Track B results native end-to-end safety or deployment performance.

### Track B score-only adapter for native-gate disagreements

The Phase I `RecommendationEngine` first excludes any record whose stored `TaskUtilityEstimate.hard_gated` is true and only then computes `CandidateSignals`. Therefore its native path does not create ranking signals for a gated candidate. A Track B score-only adapter is a separate evaluation path and must not call the native recommendation engine with gates disabled or alter Phase I code.

For every candidate in the oracle-eligible Track B pool, the adapter must use the frozen task specification, source record, evidence entries, fingerprint, and configuration snapshot to call the unchanged Phase I `TaskUtilityEstimator.evaluate` and `compute_candidate_signals` functions directly. Retain the exact returned estimate, including its native `hard_gated` flag, reason, component records, and composite utility. If Phase I gates the candidate, do not change `hard_gated`, clear its reason, recompute its composite utility as if ungated, or substitute a different utility estimate: its existing gated estimate has composite utility `0.0`, which remains the `utility_score` feature. Compute the other candidate signals from the estimate's unchanged components and frozen evidence, then apply the unchanged `score_candidate_r1` or `score_candidate_r2` function. Missing evidence/fingerprint is passed through the Phase I interfaces as represented by the frozen records; do not fill it from adjudication or a new source check. A missing estimate, invalid signal, or computation error is a task/evaluation failure to report and resolve under a predeclared rule, not a reason to remove that candidate only for one method or impute a score. For learned scoring, use only the same five prespecified signals; do not include adjudicated eligibility, native gate state/reason, relevance, or adjudication as a feature. This produces a counterfactual score-only ordering on the oracle pool, not an output the native system would emit.

Log per candidate the input candidate/task IDs, source and snapshot hashes, task-specification hash, evidence/fingerprint IDs and hashes, estimator and signal-function versions, scoring weights/configuration hash, full unmodified utility-estimate fields, resulting signal values, native gate outcome/reason as separate audit metadata, and adapter version. Record counts for (a) native-gated candidates adjudicated Track B eligible, and (b) native-pass candidates adjudicated ineligible or unresolved, by gate reason and task; never use these post-hoc labels to recompute features. Train/development eligibility and relevance may be opened only under their approved split permissions. Held-out eligibility labels remain sealed with held-out relevance labels until the approved one-shot evaluation; they cannot be used for fitting, tuning, feature construction, stopping, test-set exclusions, task selection, or score imputation.

Within Track B, distinguish static ranked lists from recommendation sets. A static ranking orders the common pool by one candidate score. A recommendation set is produced by a specified family-aware selector. Report these as separate outcomes; differences between them can reflect selection as well as scoring.

## Comparisons and native Phase I fidelity

All comparison adapters must use a fixed, one-to-one mapping from external `candidate_id` to the Phase I `internal_id`. Preserve the exact identifier string used by Phase I for tie-breaking. Missing or duplicate IDs are a preflight error; do not normalize identifiers, silently deduplicate, or change the candidate order to manufacture a tie result.

### Native R1, R2, and R3 behavior

- **R1 static ranking:** use `score_candidate_r1`, which rounds utility to four decimal places. The native sort key is `(score, internal_id)` with `reverse=True`; ties therefore order by internal ID descending.
- **R2 static ranking:** use `score_candidate_r2` and its frozen weights/formula, which rounds the composite score to four decimal places. The native sort key is `(score, internal_id)` with `reverse=True`; ties therefore order by internal ID descending.
- **R3 native recommendation:** use `score_candidate_r3` (the R2 intrinsic score) and the unchanged `select_diversified_set` implementation with the frozen Phase I configuration, including `lambda_div`, family-linkage function, and attribute-distance function. R3 sets the first candidate's marginal diversity to 1; for later candidates it uses the minimum attribute distance to any selected candidate. Its greedy comparison key is `(round(marginal_gain, 6), round(intrinsic_score, 6), internal_id)`, maximized lexicographically. It excludes candidates detected as same-family with any selected item and stops when no candidate remains; consequently it may return fewer than three. Preserve its native top-three target and do not append same-family mirrors to fill slots.

Native R1/R2 tie order is descending identifier, and native R3's rounded-key tie order is also descending identifier. A Phase II adapter with a different order is a different method, not a faithful native reproduction. Tests must compare the adapter's first three outputs with native R3 on identical inputs and fail on any mismatch.

If a gate-disabled analysis is retained, it is an offline shadow diagnostic only: it may not emit user-facing cards, be treated as a deployable baseline, or promote known-ineligible records for demonstration. It is not part of the proposed primary comparison or H1; identify and version its exact method separately before any such run.

### Pre-annotation comparison-fidelity checklist

Before assessor work starts, a no-label verification must confirm all of the following:

1. Every `candidate_id` maps one-to-one to the exact Phase I `internal_id`; missing or duplicate identifiers fail preflight.
2. R1 and R2 reproduce their Phase I formulas, score rounding, and descending identifier tie order; R3 reproduces the six-decimal greedy key, descending identifier tie order, family exclusion, and stop-on-exhaustion behavior.
3. On identical evidence, candidate inputs, native gate-pass candidates, and configuration, the raw-R2 selector fidelity path returns exactly the same ordered native R3 top-three (or shorter) output.
4. Track A receives the unfiltered pool and no annotation-derived eligibility; its serialized gate decisions and output are captured before labels are joined.
5. Before annotation, synthetic eligibility fixtures and candidate pools verify that both ranking methods receive identical oracle-filtered inputs when given the same eligibility decisions; this tests only the implementation contract. After authorized annotation and adjudication, construct the real common Track B pool from actual independently adjudicated eligibility records, subject to sealed-test access restrictions, and verify identical candidate membership and order under the approved comparison procedure. Do not expose held-out labels before authorized access.
6. The learned-versus-R2 primary comparison uses static lists, one common Track B pool, and the same score-tie order; the normalized matched-selector comparison is separately named and does not substitute for native R3.
7. Synthetic metric fixtures verify the published equations and N/A, unassessable, ineligible-output, missing-slot, and short-list rules. All fixtures use synthetic judgments and cannot contain benchmark labels.

### Matched ranking comparisons

1. **Primary proposed comparison — learned scoring contribution:** compare the learned model's static ranked list with frozen R2's static ranked list on the same Track B pool, using candidate-level macro nDCG@10. Static score ties in both methods use the Phase I stable identifier order (descending `internal_id`). This holds the pool and static-list condition constant and isolates the scoring method more directly than comparing a learned score to a diversified set. This changes the original PR proposal's RQ1/H1 comparator from R3 output to R2 static scoring and requires explicit author/supervisor approval before protocol freeze.
2. **Secondary proposed comparison — learned score under matched diversification:** apply one registered Phase II selector adapter to the learned scores and R2 scores on the same Track B pool. First min–max normalize each method's scores within the same task pool to `[0,1]`; if all scores are equal, assign every candidate `0.5`. This label-free, within-pool transform gives the unchanged diversity weight a common score range while preserving each method's within-task order. Then keep selector mechanics fixed across score inputs: same `lambda_div`, family test, attribute-distance function, six-decimal marginal-gain and normalized-score tie-key rounding, identifier tie direction, target size, and exhaustion rule. This normalized adapter is a Phase II comparison, not native R3. Separately, a fidelity fixture must pass raw R2 scores through the adapter's selector mechanics and reproduce native R3's first three outputs exactly on identical candidate inputs and native gate-pass candidates. The raw-score fidelity path is not the matched learned-versus-R2 result.
3. **Native operational reference:** report the unmodified Track A R3 top-three set, including short sets caused by gate exclusions or family exhaustion. Do not extend this output to top ten. Any top-ten selector analysis requires a separately versioned, named secondary method; its first three items must exactly match native R3 top-three under identical inputs and settings, it must retain family exclusion and exhaustion, and it must not append same-family mirrors to fill ten. It must not be presented as native R3.

R1 and retrieval-based static rankings may be reported as prespecified secondary comparators on the Track B pool. BM25, dense MiniLM, and RRF must also be evaluated in their separate candidate-generation role. For each, retain raw top-six results against the frozen catalogue snapshot and report judged-pool coverage separately. If retrieval scores are used to rank the common Track B pool, state that this is a separate ranking adapter and preserve the exact retrieval scores and tie behavior.

## Learned-ranking path

Use one query-grouped pairwise logistic linear ranker. For a candidate feature vector `x`, score `w · x`; construct within-task pairs only for candidates with unequal, assessable, adjudicated ordinal grades. Use the higher-grade candidate as target 1 and include the reverse signed-difference row with target 0. In Track B, construct ranking pairs only from the common oracle-eligible pool; the result is therefore conditional on those labels. Do not feed eligibility labels, relevance labels, task IDs, dataset IDs, popularity, or assessor decisions into the score features.

Standardize features using the fitting split only; assign each task equal total loss weight regardless of its number of non-tied pairs. Fit an L2-regularized logistic regression with no intercept, fixed solver and tolerance recorded in the run configuration. The model-training and evaluation seeds must be specified, approved, and recorded in the frozen analysis configuration before experimentation; no numeric model seed is selected by this proposal. Select inverse regularization strength `C` from `{0.01, 0.1, 1, 10}` by highest macro development nDCG@10; break ties by choosing the smallest `C` (strongest regularization). Refit once on train plus development labels with the selected `C` and normalization recomputed on train plus development. A task with no unequal assessable training pair contributes no pairwise loss and is reported; stop learned-model work if fewer than 8 of 12 train tasks contribute pairs. If every development nDCG is undefined or the fit fails, report the learned path as infeasible under this proposal and do not open test labels. No other model family, feature search, threshold tuning, or test-set stopping is permitted.

The five initial features are the existing Phase I `CandidateSignals`: fit, utility, evidence support, content coverage, and risk penalty. Compare this model with the same pairwise method trained without `evidence_support_score`; keep all other feature construction, eligible pools, task weights, optimization, and tuning rules fixed. This tests the incremental contribution of that feature in this model and is not a causal estimate of the entire evidence subsystem.

## Metric definitions and denominators

For task `t`, let `E_t` be the Track B oracle-eligible pool. Let `A_t` be its candidates with assessable relevance labels and `P_t = {i ∈ A_t : grade_i ≥ 2}`. `unassessable` is a judgment state, not relevance grade zero. It contributes no gain or hit to a ranking metric, but if returned it occupies its rank/slot. In Track A, independently adjudicated eligibility is applied only after the native run for metric classification; it never changes the native input pool or output.

For a ranked output, consider its first `k` returned positions. A returned ineligible or unresolved candidate in Track A, or an unassessable candidate in either track, is a non-hit for relevance metrics and still occupies its returned position. A position not filled by the method is a missing slot; it is not imputed as a candidate or assigned a relevance grade. Report actual output length and missing slots alongside metrics.

### Candidate-level ranked-list metrics

- **DCG@k / nDCG@k:** for returned position `r`, gain is `2^grade − 1` for assessable, eligible grades 0–3 and zero for unassessable, ineligible, or unresolved items; discount is `log2(r+1)`. A missing position contributes zero. `IDCG@k` is computed by sorting the assessable, eligible gains in the applicable task pool and taking the first `k`; `nDCG@k = DCG@k / IDCG@k`. If `IDCG@k = 0`, report N/A with reason. For Track A, adjudicated eligible labels determine metric gain only after the native output is fixed. For Track B, all methods rank the same `E_t` pool. Candidate-level nDCG does not account for family redundancy and must not be interpreted as set utility.
- **Precision@k:** report two forms to make short outputs auditable. `returned-item precision@k = H_k / L_k`, where `H_k` is the number of assessable, eligible grade-≥2 returned items in the first `k` positions and `L_k` is the number actually returned there. Unassessable, ineligible, and unresolved returned items remain in `L_k` but not `H_k`. If `L_k=0`, report N/A. `slot precision@k = H_k / min(k, |E_t|)` in Track B; for Track A use the independently adjudicated eligible pool size as `|E_t|`. Missing returned slots count in the fixed slot denominator. If the eligible pool is empty, report N/A. Report the actual list length so a high returned-item precision from a short set is not mistaken for full slot coverage.
- **Recall@k:** `H_k / |P_t|`, with eligible, assessable grade-≥2 candidates in the frozen judged pool as the denominator. If `|P_t|=0`, report N/A; do not assign zero or perfect recall. Missing output slots produce no hits but do not change the pool denominator.
- **MRR@k:** reciprocal rank of the first assessable, eligible grade-≥2 result in the first `k`; use zero if `|P_t|>0` but no such item is returned in the first `k`; report N/A if `|P_t|=0`.
- **Judged-pool Recall@6:** for each retrieval method, eligible, assessable grade-≥2 items in its raw top-six catalogue results divided by `|P_t|` for the frozen judged pool. If `|P_t|=0`, report N/A. Report numerator, denominator, and pool construction. Because retrieval outputs contribute to the judged pool, this is mixed-pool judged-pool coverage, not an unbiased retrieval-superiority estimate or full-catalogue/live-discovery recall.

**Synthetic example (metric semantics only):** suppose a task has four oracle-eligible candidates, with assessable grades 3 and 2 for two candidates and two unassessable labels. A method returns the two assessable relevant candidates only. Its returned-item precision@3 is `2/2 = 1.0`, while slot precision@3 is `2/min(3,4) = 2/3`; one of the three available recommendation slots is unfilled. Recall@3 is `2/2 = 1.0`. If an unassessable item were returned instead, it would not become a human grade 0, would produce no hit, and would occupy a returned slot. This example is synthetic and is not benchmark evidence.

### Recommendation-set measures

Report set measures separately for native Track A R3 and the matched Track B selector results:

- **Set returned-item precision:** assessable, eligible grade-≥2 selected items divided by selected items. **Set slot precision@3:** the same numerator divided by `min(3, eligible-pool size)`; missing selections count against the available slot denominator. **Set recall:** the numerator divided by `|P_t|`. Each is N/A when its denominator is zero. Always report selected-set size and shortfall from three.
- **Mean selected relevance grade:** arithmetic mean over selected items with assessable, eligible relevance labels only; report the number assessed and assessment coverage. Do not assign grade zero to unassessable items. Report N/A if no selected item is assessable and eligible.
- **Family redundancy:** same-family selected pairs divided by selected pairs whose family relation is known. Report unknown-family pairs separately; if there are no pairs with known relation, report N/A. Do not define a zero-item/single-item set as zero redundancy.
- **Source/family coverage:** report distinct known sources/families and selected-set size; report unknown family identities separately.
- **Attribute diversity:** use the frozen Phase I mean pairwise attribute-distance function and definition. For a singleton, report the implementation-defined value 0 with set size one; for a zero-item set report N/A. Keep this measure separate from relevance; more diversity is not inherently better.

**Synthetic short-set example:** if a selector returns two eligible, assessable grade-≥2 candidates from a task with four eligible candidates and a third slot is unavailable, returned-item precision@3 is `2/2 = 1.0`, slot precision@3 is `2/3`, and selected-set size is `2/3`. This is a short-output description, not a basis to call either value the sole set-quality metric.

### Native gate and constraint outcomes

For Track A, report the complete native gate decision table against each applicable adjudicated mandatory constraint, including excluded and passed candidates from the unfiltered input pool. For emitted top-three R3 outputs, report: (i) confirmed-violation outputs divided by emitted outputs with assessable applicable constraint judgments; (ii) policy-ineligible/unresolved outputs separately; (iii) outputs with any unknown mandatory state separately; and (iv) outputs whose constraint status is unassessable separately. If a denominator is zero, report N/A. Do not count unknown or unassessable as a confirmed violation. Do not collapse these outcomes into one accuracy or safety score.

Track B is oracle-filtered, so it cannot estimate gate correctness or a gate-on violation rate. Do not report the absence of ineligible records in the Track B input as evidence of system safety.

### Evidence, provenance, diversity, and efficiency

- **Evidence support:** among output candidates, report the proportion of applicable task-critical facets whose evidence state/source is present and consistent with the independent packet, plus missing, unknown, and conflicting counts. No calibrated-confidence interpretation.
- **Provenance traceability:** report source-reference coverage (claims with resolvable source ID/URI and observation timestamp divided by claims requiring provenance) and a blinded source audit of the prespecified 20% sample of output claim references. Report coverage and sampled support correctness separately.
- **Diversity:** report mean pairwise Phase I attribute distance and same-family redundancy separately from relevance.
- **Efficiency:** record wall time, peak process RSS, environment, software/package/model versions, warm/cold state, cache state, seed, and network-egress observation. Measure candidate acquisition/index construction separately from per-query ranking and report end-to-end totals. Use isolated runs for memory comparison; do not assign M2's shared 453.22 MiB RSS to one backend. Compare M8's 33.11 MiB/327.49 ms only as its own frozen recorded path. Report whether Phase II runs meet or exceed the M0 design ceilings of 128 MiB and 20 seconds without treating those limits as evidence of quality.

## N/A handling, sensitivity analyses, and family-aware relevance

Never convert unassessable relevance to human grade zero. For every metric and method, publish per-task value or N/A plus reason, denominator, returned-list length, assessability, eligibility counts, and task-family cluster. Zero eligible candidates or zero eligible, assessable positive candidates make metrics requiring those denominators N/A; do not silently drop such tasks or count them as successful results.

For each paired contrast and metric, define the common evaluable test-task set as the intersection of tasks where both methods' metric is defined under the same pool and labels. Use that same set for both methods and all paired task differences. Report all 18 planned test tasks, N/A counts/reasons by modality and method, cluster counts, and the shared evaluable set. Do not compare means calculated over different task sets. If a common denominator is expected by construction (as for Track B nDCG on the same eligible pool), verify and report it; disagreement indicates a pipeline defect.

The primary ranking analysis is candidate-level. Add one family-aware sensitivity using only documented dataset-family links: treat each documented family as one unit with gain equal to the maximum assessable, eligible member gain in that family; at the first ranked occurrence of that family, assign that gain and assign zero gain to later occurrences of the same family. Compute ideal DCG by sorting the documented-family gains. Candidates without a documented family link remain singleton families in this view and their fraction is reported; this does not establish that unknown families are independent. Report the Phase I detector-inferred-family sensitivity separately, never merge it with the documented-family result. This analysis asks whether candidate-level nDCG conclusions depend on counting documented mirrors more than once; it is not the primary estimand.

For unassessable labels, the primary nDCG/precision/recall rules above give no relevance gain/hit while preserving returned rank/slot position. A prespecified **assessable-only sensitivity** removes unassessable candidates from each ranked list and pool denominator, compacts remaining ranks, and recomputes the metrics. Report the changed eligible/assessable counts and label it as ranking conditional on assessability. Never assign an inferred relevance grade to an unassessable item.

## Proposed statistical analysis specification (pending approval)

The task-family cluster is the independent sampling unit. All task briefs in a family cluster remain in one split and move together in resampling. For a paired comparison, calculate each task's metric difference on the common evaluable set. Do not treat candidate pairs, label pairs, or pairwise model-training examples as independent test observations.

The proposed primary estimand uses **fixed equal modality weights**: within each of text, tabular, and image, average the paired task differences equally across common evaluable tasks in that modality; then take the unweighted mean of the three modality means. A modality with no common evaluable tasks makes the pooled contrast N/A; do not reweight the other modalities to fill its share. Report the task-weighted overall macro mean as a secondary descriptive value so the fixed modality estimand is explicit.

**PROPOSED — PENDING AUTHOR/SUPERVISOR APPROVAL.** Use 10,000 paired replicates. Define each task-family/dependency cluster's anchor modality from its full frozen held-out task membership: the most represented modality, breaking ties in fixed order text, tabular, image. Assign a multimodality cluster to exactly one anchor stratum, but carry all of its task rows together whenever selected. Within each anchor stratum, sample the observed number of common-evaluable clusters with replacement. The canonical cluster order is the lexicographically sorted stable cluster ID list within text, tabular, image order. Repeated cluster selections retain multiplicity: every selected copy contributes all of that cluster's common-evaluable task rows to the task-level mean for each task's own modality. First calculate equal-task means within each modality, then combine the three means with fixed weights of 1/3. Thus tasks remain equally weighted within modality while dependency is retained at cluster selection. A modality absent from a replicate makes that replicate undefined; do not redraw it.

The proposed randomization implementation is NumPy `Generator(PCG64(seed))`, proposed seed `20261029` unless the approved registry versions it, NumPy version `2.5.2`, and `Generator.integers(0, n, size=n, dtype=int64)` per nonempty stratum in text/tabular/image order. This is a versioned implementation choice, not an approved scientific decision. Store every replicate's selected zero-based cluster indices (duplicates included), replicate index, recomputed statistic or null, and undefined modality list in canonical UTF-8 JSON; hash the exact serialized bytes with SHA-256. The verifier checks the recorded draws against the registered seed and pinned generator, then independently reconstructs values from the paired task outcomes. The serialized indices permit replay without a future PRNG implementation; the seed and runtime metadata document how the draws were generated.

For a pooled primary interval/decision rule, require at least **12 common-evaluable test task-family clusters overall and at least four distinct clusters contributing one or more tasks in each modality**. A multi-modality cluster counts once toward the overall total and once in each modality it contains. This is a minimum reporting gate, not a power claim. If it is not met, report per-task and modality summaries, mark the pooled confirmatory interval and H1 decision N/A, and do not claim that the methods are equivalent. Apply the same minimum to the family-disjoint sensitivity; otherwise report per-task results and mark its pooled result N/A.

Use a two-sided 95% percentile interval. The proposed quantile convention is Hyndman–Fan type 7: for sorted defined replicate values `x[1..n]` and probability `p`, set `h=(n−1)p`, `j=floor(h)`, `g=h−j`, and interpolate `(1−g)x[j+1] + g x[min(j+2,n)]` using zero-based indexing for implementation. This rule is **PROPOSED — PENDING AUTHOR/SUPERVISOR APPROVAL**. Retain undefined replicates without redrawing and use the planned 10,000 as the undefined-rate denominator. At most 100 undefined replicates are tolerated; quantiles are computed from defined values only and the undefined count is reported. More than 100 undefined replicates, zero defined values, an absent modality, or failure of the cluster gate suppresses the interval and H1 decision. Require at least 12 common-evaluable clusters overall and at least four distinct contributing clusters for every modality; this is a reporting gate, not a power claim. A cluster containing multiple modalities counts once overall and once for each modality it contributes to. With at most 18 held-out tasks and likely fewer independent clusters, intervals may be unstable and broad; no high-power or beyond-frame generalization claim is permitted.

A future implementation should replay the registered draws and replicate statistics from task-level paired outcomes, derive the stated percentile endpoints, and recompute the H1 decision from authorized frozen inputs. Until the statistical choices are approved and the replay can be independently reviewed, any eventual point estimate must be reported descriptively without a confirmatory interval or decision. A public redacted record must not expose private draws or labels; its evidence chain requires an external authorization mechanism. This proposal does not implement or certify bootstrap verification.

### Mandatory analysis registry and held-out task accounting

Before any held-out labels are opened, the primary analysis must be represented by a versioned registry entry. H1 is proposed as Track B, `R2_static` versus `learned_static`, candidate-level static ranking, `nDCG@10` (`k=10`), on the common oracle-eligible pool. Its denominator is ideal gain over assessable oracle-eligible candidates; a task with zero ideal gain is N/A and remains in task flow. The modality weights are fixed at one third each. The registry records the bootstrap and decision rule (+0.03 estimate and interval lower endpoint above zero), plus artifact references. These registry and freeze records are proposed data-governance requirements; the tooling to validate them is future work and is not included in this design-only proposal.

For H1, `common_task_ids` means the complete frozen held-out task accounting frame, including tasks with N/A metrics. It must enumerate every held-out task exactly once. For each such task, retain one metric row for each registered method, including paired N/A rows; recompute candidate-level nDCG from the stored ranking output and adjudicated task-candidate outcomes. Derive the evaluable subset from those paired rows, never from a manually supplied subset. A method-specific evaluability mismatch is invalid for the paired primary comparison. Any unsupported task N/A or omitted task invalidates completed confirmatory analysis. If the set cannot estimate all three modality means, the H1 result is `not_estimable`, with no point estimate, interval, or decision; do not substitute zero.

The completed H1 result records the recomputed equal-modality estimate, task and evaluable-task denominators, interval-reporting state, undefined bootstrap replicate count, interval (when allowed by the registered minimum-cluster gate), and the decision-rule outcome. A result may state `criterion_not_met`; this is not equivalence. A future public release should remove task-level metric rows, test labels, and evaluable task IDs. It may retain approved aggregates and a reference to the frozen evaluation history only after an externally authorized review. A future validator must not claim to recheck inaccessible labels.

For first-pass assessor agreement, calculate weighted kappa on mutually assessable first-pass relevance grades, exact and within-one-grade agreement, assessability agreement, and exact constraint-state agreement before adjudication. A cluster-aware uncertainty analysis for agreement may be considered, but the resampling unit, modality handling, replicate count, seed, kappa weighting convention, minimum-cluster rules, and undefined-replicate policy remain unresolved and require author/supervisor approval before protocol freeze. Agreement describes these assessors and sampled tasks; it is not a measure of model performance. The custodian must not expose test-label agreement details to developers before one-shot evaluation.

## Proposed hypotheses and decision rules (not yet approved)

These are design proposals, not registered or achieved results. Changing the primary comparator changes the original PR's RQ1/H1 and requires author/supervisor approval.

- **H1 (primary proposed):** on the shared evaluable held-out Track B tasks, the learned static ranker has higher macro nDCG@10 than frozen R2 static ranking. The proposed +0.03 difference is a decision threshold, not an expected result. The proposed criterion is an observed estimate of at least +0.03 with a paired 95% interval whose lower endpoint is above zero. Meeting that decision rule would not establish that the population effect is at least +0.03. If the estimate is below +0.03 or the interval includes zero, the criterion is not met; report the estimate, interval, every task difference, and limitations. Failure to meet it is inconclusive, not evidence of equivalence.
- **H2 (secondary proposed):** the five-signal model has higher macro test nDCG@10 than the matched four-signal model without `evidence_support_score`; report paired task differences and interval. Do not claim the entire evidence subsystem caused an effect.
- **H3 (RQ3b; Track A descriptive safety criterion):** report whether native gate-on R3 outputs contain confirmed mandatory-constraint violations or policy-ineligible/unresolved candidates. A failure is reported regardless of relevance; an observed zero is bounded to the evaluated pool and is not a universal guarantee. Unknown and unassessable outcomes remain separate.
- **H4 (RQ3a; descriptive retrieval coverage):** report BM25, dense MiniLM, and RRF judged-pool Recall@6 with per-task values and the proposed cluster-bootstrap intervals. The mixed judged-pool construction prevents full-catalogue recall or an unbiased catalogue-wide superiority claim.

Only H1 is proposed as confirmatory. Report H2 and H4 estimates and all three H4 retrieval pairwise contrasts with unadjusted intervals labeled exploratory; report H3 as counts and denominators. Make no significance or superiority claim from any secondary analysis. This is the proposed multiplicity policy; if authors want confirmatory claims across secondary comparisons, the family of contrasts and multiplicity adjustment must be preregistered before labels are opened. Report null and negative results.

## Decisions required before protocol freeze

Authors and supervisor must explicitly approve: (1) Option A or B after the separate calibration and workload review; (2) the revised RQ1/H1 comparator of learned static versus R2 static; (3) whether to retain the min–max-normalized matched-selector comparison as a separate Phase II method; (4) the fixed equal-modality estimand, cluster bootstrap, minimum reporting gate, and exploratory multiplicity policy; and (5) task/candidate source terms, assessor consent, data retention, and test-custody arrangements. Approval of these proposed definitions is not authorization to begin benchmark acquisition, annotation, training, or test evaluation.

## Exclusions, seeds, and reproducibility

Before evaluation, freeze and hash the task/candidate manifest, rubric, annotation exports, adjudication file, code revision, configuration, feature definitions, dependency lock, dense-model revision where used, and analysis script. Record seeds and timestamps. No final-test experiment may run until these items and the decision rules are approved and frozen. Apply only predeclared exclusions; publish a flow count by split and reason. No Phase II result is created by this protocol revision.
